# Backlog drafts

Exploratory updates written in February and March 2026 that never entered the numbered sequence. The folder numbers do not line up with the main Updates (several were renumbered in the 2026-03-12 reorganization `1c4aba2`, and some titles inside the tex still carry their old numbers). Pieces of several were folded into `Updates/Drafts/draft1.tex`. Status below is checked against the repo as of 2026-10-22.

**Update4-FlashAttention3Blackwell** (February 2026, `1cfbe73`). Diagnoses vLLM failing with FlashAttention 3 on the RTX 5090 ("Sinks are only supported in FlashAttention 3", early CUDA init) and fixes it by moving the `get_flash_attn_version` import from module scope into the function in `mm_encoder_attention.py`. Became real work: [`deployment/patches/vllm-blackwell-fa3.patch`](../../../deployment/patches/vllm-blackwell-fa3.patch) (upstream issue vllm-project/vllm#22279, local note [Issue_22279_...md](../../../References/Bookmarks_RDMA/thesis_refs/Issue_22279_FlashAttention_3_fails_on_Blackwell_GPUs.md)), and the 142 to 164 tok/s (+15.5%) Llama 3.2 1B result that the top-level README cites, which exists only in this tex and in `draft1.tex`, with no results file. Two corrections: the tex says PyTorch reports compute capability (10, 0) for the RTX 5090, but the 5090 is SM_120, compute capability (12, 0); and the repo patch is an import-order fix, not a kernel. If the thesis describes an FA3 kernel for SM_120 it has to be an mma.sync kernel (SM_120 has no `tcgen05` or `wgmma`), and that kernel is not in this repo. Suggest: keep as an appendix note, rerun the throughput number with a saved JSON before citing it.

Suggest: merge the measured parts into the thesis testbed chapter, drop the projections.

**Update8-InfrastructureRDMATesting** (February 2026, `ea53ad1`; file is `update3.tex`). Lab and home infrastructure bring-up and the first measurements: SoftRoCE between server 1 and server 2 at 0.92 Gb/s and about 190 us, hardware RoCEv2 on the ConnectX-4 at 50.62 Gb/s (`ib_write_bw` loopback, limited by PCIe 3.0 x8) and 0.71 us, the `CONFIG_INFINIBAND_PEER_MEM` blocker for `nvidia-peermem` on the Proxmox kernel and the PVE kernel rebuild, ConnectX-4 SR-IOV, the TTPoe build, vLLM multi-node with Ray. Became real work: these are the only measured hardware RoCEv2 numbers in the repo, and the source of the "0.92 Gb/s" figure the top-level README attributes to Update 4 (it is a two-node `ib_write_bw` result, not server 2 loopback). No results files; the numbers live only in the tex. Suggest: merge into the thesis testbed chapter, and rerun the perftest numbers through notebook 00 so they are saved as JSON.

**Update11-WorkFirstScheduling** (February 2026; title inside says Update 12). Applies the Cilk-5 work-first principle, work stealing, NUMA and Ryan Fleury's lane model to tensor transport. Merged into `draft1.tex` ("Work-First Scheduling for Tensor Transport"). Note the acronym collision this created: `draft1.tex` expands WFA as "Work-First Algorithm", the `wfa_classifier.py` docstring says "Work-First Adaptive classifier", and the proposal and later updates use Weighted Finite Automaton. The thesis should use one expansion. Suggest: keep the work-first argument as motivation for keeping the hot path short, rename it so it does not collide with WFA.

**Update12-USB4Investigation** (February 2026). SoftRoCE over a USB4 network link between server 1 and server 2, with only projected numbers. Its motivation records the earlier baseline over 2.5 GbE Realtek interfaces: 0.91 Gb/s `ib_write_bw` and 111.86 MB/s UCX `tag_bw`. That conflicts with draft Update8's 0.92 Gb/s "over 10G Ethernet" and is the source of the README's "UCX tag_bw cross-node 111.86 MB/s" (which the README attributes to Update 4). Which link produced which number needs to be pinned down before either is cited. Suggest: drop USB4; keep the measured baseline only once the link is confirmed.

Suggest: merge the design points that the C code actually uses (pre-registered arena, split completion polling) into the thesis implementation chapter; drop the Rust targets table.
