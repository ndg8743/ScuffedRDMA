\section{Summary}

Update 7 placed libscuffedrdma among the libfabric, UCX and DOCA stacks and noted that libfabric's endpoint model matches the hot/cold split directly. This update moves the middleware onto libfabric and carries it up to vLLM.

What exists now:
\begin{itemize}
\item \texttt{libscuffedfabric}: the dual pool on libfabric. Each class (hot, cold) gets its own endpoint and CQs, and can use its own provider and endpoint type (\texttt{FI\_EP\_MSG} or \texttt{FI\_EP\_RDM}).
\item \texttt{libscuffedverbs}: the same C API on raw libibverbs RC queue pairs, so both stacks run one benchmark source.
\item \texttt{FabricBlobChannel}: a Python blob channel over the pool, and \texttt{ScuffedRdmaConnector}, a vLLM V1 KV connector that moves disaggregated-prefill KV through it.
\item A baseline path through vLLM's \texttt{NixlConnector} with NIXL's own \texttt{LIBFABRIC} backend, next to the usual UCX one.
\item Around the transport: unified telemetry, a WFA with learned weights, the rule-tree policy engine, the PMP storage arm and an NVMe tier (Section~\ref{sec:stack}).
\item Nine Jupyter notebooks. Each runs in a local mode (smoke tests on any machine) and a cluster or GPU mode that produces the numbers.
\end{itemize}

Everything below was built and run end to end on libfabric 1.17's \texttt{tcp}, \texttt{tcp;ofi\_rxm} and \texttt{shm} providers, and the connector passes its tests against vLLM 0.24.0's own base class. None of those runs are results. The tables are filled by notebooks 01 to 03 and 06 on Cerberus and Chimera, and by notebook 08 on a single desktop GPU.

\section{Why libfabric}

\begin{enumerate}
\item \textbf{The endpoint model fits the design.} libfabric exposes connected (\texttt{MSG}) and reliable-unconnected (\texttt{RDM}) endpoints, completion counters as a lighter alternative to CQs, selective completion, and wait objects on CQs~\cite{grun2015,fi_endpoint,fi_cntr}. Hot traffic wants the cheapest completion; cold traffic wants a deep queue and a thread that sleeps. With libibverbs both are built by hand. With libfabric they are configuration.
\item \textbf{GPFS runs on it.} IBM Storage Scale uses libfabric under its RDMA path, so a cold class on the same stack is the natural route for KV spill to a GPFS tier (Update 6).
\item \textbf{The serving stack is already moving there.} NIXL ships a libfabric backend that vLLM can select~\cite{nixl_lf,vllm_nixl}, NVIDIA's Dynamo setup for AWS selects it for EFA~\cite{dynamo_efa}, and EFA itself is reached through libfabric~\cite{chen_efa}. fabric-lib, a point-to-point RDMA library for LLM systems, builds its API on one-sided \texttt{WriteImm} with an \texttt{ImmCounter} for completion and reaches 400\,Gbps on ConnectX-7 and EFA~\cite{fabriclib}. Those are the same two primitives this pool uses (\texttt{fi\_writedata} and the remote-write counter in E5).
\item \textbf{The stack choice is measurable.} Smith's MUG'23 comparison concludes that libfabric and UCX ``both provide very similar performance benefits''~\cite{smith_mug23}. EPCC's ARCHER2 study found little difference in OSU micro-benchmarks but large application-level differences in \texttt{MPI\_Alltoallv}~\cite{bareford2022}. Micro-benchmarks alone do not settle it, so this update measures under mixed traffic and at the connector level too.
\end{enumerate}

\section{Provider behavior found while building}

From libfabric 1.17's \texttt{tcp}, \texttt{tcp;ofi\_rxm} and \texttt{shm} providers in a two-core container. Whether the verbs provider shares any of these is part of the cluster run.

\begin{itemize}
\item \textbf{\texttt{tcp} needs target-side CQ reads despite \texttt{FI\_PROGRESS\_AUTO}.} With the target not reading the cold CQ, a 1\,MB write stream stalled after about three writes. The benchmark server now runs a yielding progress thread on the cold endpoint for every provider.
\item \textbf{Remote-write counters are not uniform.} \texttt{tcp} advertises \texttt{FI\_RMA\_EVENT} but did not increment an endpoint-bound counter, and \texttt{fi\_mr\_enable} on an \texttt{FI\_RMA\_EVENT} MR returned \texttt{-FI\_ENOSYS}. \texttt{ofi\_rxm} does not offer it. \texttt{shm} counts through the endpoint. The library binds both ways and the benchmark probes one write each way before trusting a counter.
\item \textbf{Connection-request info drops optional caps.} The passive side's \texttt{FI\_CONNREQ} info lacked \texttt{FI\_RMA\_EVENT} although the listener asked for it. The library copies it back.
\item \textbf{\texttt{ofi\_rxm} connects on first use.} The initiator's first write spins on \texttt{-FI\_EAGAIN} until the target makes progress. Posting is bounded (60\,s), so an idle peer becomes an error instead of a hang.
\item \textbf{\texttt{shm} does not advertise write-after-write ordering} for RMA, so the sentinel mechanism is skipped there.
\item \textbf{With one endpoint the target cannot tell classes apart.} The single-endpoint baseline therefore measures exactly the coupling the dual pool removes.
\end{itemize}

\section{libfabric under vLLM}

\subsection{FabricBlobChannel}
The connector needs ``send this named blob, receive named blobs'', not raw writes. \texttt{FabricBlobChannel} provides that over the pool with credit-based slots. Each blob goes with \texttt{fi\_writedata} into a receiver slot on the class the sender picks (cold by default, hot when the WFA tags it), with the slot number and a DATA tag in the immediate. The receiver returns a credit as an 8\,B write on the hot endpoint (CREDIT tag + slot). Credits and control blobs do not share an endpoint with bulk KV, which is the head-of-line property the thesis is about, applied to the connector's own protocol. A \texttt{TcpBlobChannel} with the same interface is the fallback and the baseline.

\subsection{ScuffedRdmaConnector}
An out-of-tree \texttt{KVConnectorBase\_V1} loaded through \texttt{kv\_connector\_module\_path}. The proxy sends the prompt to prefill with \texttt{max\_tokens=1} and a transfer id. Each attention layer's \texttt{save\_kv\_layer} gathers that request's paged blocks, copies them to host memory, encodes them (raw bfloat16, or scuffedQuant for the cold path) and queues one blob per layer. The WFA tags each blob hot or cold. Decode reports the prompt as externally matched, waits per layer, and scatters into its own paged cache. Layers that never arrive go back to vLLM through \texttt{get\_block\_ids\_with\_load\_errors} and are recomputed. If the libfabric channel cannot open, the connector falls back to TCP and records a \texttt{tcp\_fallback} telemetry event.

Staging through host memory is a deliberate choice for this hardware: Tower 2's Proxmox kernel lacks \texttt{CONFIG\_INFINIBAND\_PEER\_MEM}, SoftRoCE has no GPUDirect path, and neither does a desktop GPU under WSL2. It costs a device-to-host copy per layer. E7 and E8 show how much of TTFT that is.

The connector was written against vLLM \texttt{620e8924} (April 2026). Its tests now also pass against vLLM 0.24.0, the version a fresh install resolves today: method signatures against the 0.24.0 source, import and subclass check against the installed package, and a producer to consumer run through vLLM's own \texttt{KVConnectorBase\_V1} (CPU, no model).

\subsection{NIXL's libfabric backend as the baseline}
vLLM reads NIXL backends from a \texttt{backends} list in \texttt{kv\_connector\_extra\_config}, default UCX~\cite{vllm_nixl}. Setting it to \texttt{LIBFABRIC} is a one-line change. That makes the stock stack's libfabric path a direct baseline: same model, same proxy, same sweep, different connector. The launcher has it as \texttt{CONNECTOR=nixl-libfabric}.

Reading the plugin at NIXL commit \texttt{d642316} (22 Oct 2026)~\cite{nixl_lf}:
\begin{itemize}
\item Provider discovery asks for \texttt{FI\_EP\_RDM} with \texttt{FI\_MSG}\,\textbar\,\texttt{FI\_RMA} and takes \texttt{cxi}, then \texttt{efa}, then \texttt{tcp}, then \texttt{sockets}. \texttt{verbs} is not in that list.
\item Its README lists libfabric 1.21 or newer and GPUDirect RDMA as requirements, and AWS EFA as the only validated hardware.
\end{itemize}
So on Cerberus and Chimera (SoftRoCE) and on the towers (ConnectX-4 without peer memory), NIXL's libfabric backend can at most run over libfabric \texttt{tcp}, and may not start at all. If it does not start, the error is the result and goes in the table as such. The contrast is the point: the libfabric path the serving stack ships is shaped around EFA and Slingshot with GPUDirect, while this pool targets verbs on commodity RoCE with host staging.

\section{The rest of the stack}
\label{sec:stack}

Built this month, around the transport. All of it has tests and a notebook.

\begin{itemize}
\item \textbf{Telemetry} (\texttt{middleware/telemetry.py}). One \texttt{SignalVector} per transfer (size, role, phase, QP class, queue depth, completion latency, inter-arrival), per-class counters including QP errors, reconnects and TCP fallbacks, log-bucketed latency histograms, and Prometheus export. The pyverbs pool, the libfabric pool and the connector all report into it, so the classifier, the policy engine and the evaluation read the same numbers.
\item \textbf{Learned WFA} (\texttt{wfa\_learner.py}, notebook 04). Transition weights fit by gradient descent on \texttt{SignalVector} features, with phase-by-size terms so each phase can have its own size cutoff. On synthetic traces the static threshold classifier routes most decode KV deltas cold: they fall in its 4\,KB to 256\,KB band, where it routes by access count, and most have not been seen often enough to go hot. The learned weights recover the labeling rule. That is a synthetic result and partly by construction, since the oracle defines decode deltas as hot. The real test is training on telemetry dumps from the cluster runs, labeled by measured completion latency.
\item \textbf{Rule-Node Expression Trees} (\texttt{middleware/policy/}). Boolean trees over signals and context (GPU memory, link utilization), tried in priority order, deciding route (hot, cold, spill) and compression. Classifiers plug in as leaves, so the WFA is one input to the policy, not the policy.
\item \textbf{PMP storage arm} (\texttt{pmp\_controller.py}, notebook 07). A third bang-bang arm for spill that activates above a GPU-memory watermark, with hysteresis. Below the watermark the two-arm controller from Update 4 is unchanged.
\item \textbf{NVMe tier} (\texttt{storage\_tier.py}, notebook 07). Spill and retrieve with coalesced \texttt{pwrite}, CRC-checked reads, extent reuse, optional \texttt{O\_DIRECT}, gated by the policy or PMP decision.
\item \textbf{scuffedQuant wire format.} Indices are now bit-packed and \texttt{CompressedKV.nbytes} reports packed bytes. At head\_dim 64, 3 bits and a 256-bit QJL sketch, that is 2$\times$ against FP16.
\item \textbf{NCCL net plugin} (\texttt{middleware/nccl\_plugin/}) builds. An NCCL and vLLM run on it is still open.
\end{itemize}

\section{Corrections}

\begin{itemize}
\item The 8\,$\mu$s cross-node figure is withdrawn. The Python pool from Update 4 did not check completion status, so failed or flushed writes counted as fast completions, including 8\,MB writes that ``completed'' in about 8\,$\mu$s, which 10GbE cannot do. The pool now raises on a bad status and notebook 01 re-runs it.
\item The scuffedQuant ratio quoted as 4$\times$ against FP16 was against FP32. It is 2$\times$ against FP16 (above).
\item Several README rows (SoftRoCE bandwidth, single-QP p50, dual-QP overhead, FA3 speedup) cited sources that do not hold them. They are removed and re-measured where they matter.
\end{itemize}

\section{What the comparison can and cannot show}

\begin{itemize}
\item On SoftRoCE the verbs provider and native verbs reach the same rxe device, so their difference is libfabric's software path. The ConnectX-4 runs separate software cost from a hardware path that is no longer the bottleneck.
\item rxe processes packets in a kernel thread. If it saturates, separate QPs share it and dual-endpoint gains shrink regardless of library. E3 shows whether that happens.
\item NIXL's libfabric backend runs here over \texttt{tcp} at best, so E8 compares this pool against NIXL's libfabric path as it behaves on commodity RoCE, not on EFA.
\item E7 runs on one host through shared memory. It isolates connector and vLLM overhead; it says nothing about the network.
\end{itemize}
